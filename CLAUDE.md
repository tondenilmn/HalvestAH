# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

Cloudflare Pages deployment of the AH betting analysis tool. Fully static (no backend server) — all CSV processing, filtering, and scoring runs client-side in `static/app.js`. The one server-side component is a Cloudflare Pages Function at `functions/api/scrape.js` for CORS-bypassed odds fetching.

## Running Locally

```bash
# Regenerate manifest after adding/removing CSVs in static/data/
node build.js

# Serve locally with Cloudflare Pages dev (includes Functions support)
npx wrangler pages dev static --port 8788

# Or plain HTTP server (Functions won't work, scrape feature unavailable)
npx serve static
# Alternative: python -m http.server 3000 --directory static
```

## Deploying

```bash
node build.js && npx wrangler pages deploy static --project-name=<your-project>
```

Or connect the repo to Cloudflare Pages with build command `node build.js` and output directory `static`.

## Architecture

Everything in the Python desktop app (`constants.py`, `data.py`, `engine.py`, `stats.py`, `live_odds.py`) is ported into `static/app.js` as a single file. Keep these in sync if the Python logic changes.

`app.js` structure (top-down):
1. **Constants** — `LINE_THRESH`, `VALID_LINES`, `TL_CLUSTERS`, `ADV_TL_RANGES`, `SIGNAL_UI_TO_ENGINE`, `BETS`, `COL_MAP`
2. **Data layer** — `normaliseRow`, `parseScore`, `oddsDir`, `moveDir`, `processRow`, `loadCsv`
3. **Stats** — `pct`, `zScore`, `wilsonCI`, `stability`, `minOdds`
4. **Engine** — `applyConfig`, `applyGameState`, `scoreBets`, `traceConfig`, `discover`
5. **Live odds** — `computeLiveOdd` (Poisson time-decay, 2H bets only)
6. **App state & DB** — `state` object, `_db`, `_fileInfo`, `autoLoadData`
7. **UI** — event handlers, `switchTab`, `analyzeMatch` (Manual), `runDailyDashboard` (Dashboard), `pollLiveMatches`/`renderLiveGames`/`openLiveMatchDetail` (Live Games), render functions

## Key Constants (app.js)

- **`LINE_THRESH = 0.12`**, **`ODDS_THRESH = 0.06`**, **`TL_THRESH = 0.12`**: matching tolerances for AH line, odds, and TL respectively.
- **`DEFAULT_MIN_N = 15`**, **`MIN_Z = 1.5`**: minimum sample size and z-score for Match Analysis results — this is the floor for a bet to show at all, not a confidence bar (see `sampleTier` below).
- **`sampleTier(n, minN)`** (revised 2026-08-28): the `n=X` badge shown next to every bet (Manual Analysis, Dashboard, Live Games) — `low` (< `minN`, red), `mid` (`minN`–49, yellow), `good` (50-99, blue), `high` (≥100, green). Previously only 3 tiers with `high` starting at 50; raised after walk-forward backtesting found sample sizes in the tens (n=3-56, per-month) swung wildly (-48% to +137% ROI on the same bucket — `telegram/backtest_l2_by_favline.js`'s STRONG-favourite bucket), while bands with n in the hundreds per month stayed consistent across all 19 held-out months. n≥100 is where the evidence actually supports calling a historical rate "solid," not n≥50.
- **`VALID_LINES`**: `[0.00, 0.25, 0.50, 0.75, 1.00, 1.25, 1.50]` — includes level ball (0.00). Rows outside ±0.12 of a valid line are excluded.
- **`TL_CLUSTERS`**: named ranges `<2`, `2-2.5`, `2.5-3`, `>3` for TL cluster mode.
- **`ADV_TL_RANGES`**: finer ranges `1.5-2`, `2.25-2.75`, `3-3.5` for advanced TL range mode.
- **`SIGNAL_UI_TO_ENGINE`**: maps UI labels (`STEAM`→`IN`, `DRIFT`→`OUT`) to engine values.
- **`MIN_Z_DISC = 2.0`**: higher bar for Config Discovery (sweeps ~18k combos).

## Level Ball (0.00 Line)

When `ahHc ≈ 0`, the favourite is determined by lower closing odds (more likely to win). `favLc = 0.0`, `favLo = |ahHo|`.

## League Tier Classification

Rows are tagged `TOP` / `MAJOR` / `OTHER` at load time via `_T1_RULES` / `_T2_KEYS` in `app.js`. The UI exposes a tier filter (All / TOP / MAJOR / OTHER) that restricts the entire database before analysis. `TOP` = top 5 European leagues + main UEFA club competitions; `MAJOR` = other strong national/continental leagues; `OTHER` = everything else.

## Filter Modes (applyConfig)

**Basic mode** (`state.filterMode === 'BASIC'`): signal-based — filters by `fav_odds_move`/`dog_odds_move`/`tl_move` direction, or by odds tolerance if tolerance toggles are on.

**Advanced mode** (`state.filterMode === 'ADVANCED'`): each signal dimension has its own on/off toggle (`advLmOn`, `advOddsTolOn`, `advHomOn`, `advAomOn`, `advTlmOn`, `advOvTolOn`, `advOvmOn`, `advUnTolOn`, `advUnmOn`) and can mix signal direction, raw odds tolerance, or TL range independently.

**TL filter priority** (inside `applyConfig`):
1. `cfg.tl_range` (exact range from `ADV_TL_RANGES`) — takes priority
2. `cfg.tl_cluster` (named cluster from `TL_CLUSTERS`)
3. `cfg.tl_c` (exact value ±0.13)
4. `cfg.tl_o` (opening TL exact match ±0.13)

`over_move` and `under_move` are tracked per row and filterable independently.

## Hash Store & FEEDS Card (`functions/api/hashes.js`, `static/feeds.js`, added 2026-10-04)

Every function (`livescore.js`, `upcoming.js`, `livematch.js`, `hashes.js`) gets its three book hashes — Bet365, Sbobet, Bet365 Live — from `resolveHashes(env)` in `livescore.js`: **KV (`HASHES_KV` binding, key `hashes`) > env var > constant**, re-resolved on every request. KV holds whatever was last pasted in the app or last auto-discovered, each with `{hash, at, by}`. The one-time setup is a KV namespace bound to the Pages project as `HASHES_KV`; without it everything works as before (env > constant), just without saving.

- **FEEDS card** (top of the MATCHES tab's left panel, opens itself when a feed is broken): `GET /api/hashes` probes each hash's livegame file and reports ok / stale / wrong / unverified, plus where the hash comes from. A definitely-stale feed gets one discovery round (`healHashes`) and a working replacement is saved. The paste box `POST /api/hashes {book, url}` extracts the 40-hex hash and only saves it if it is the right kind of feed with data; `HASH_ADMIN_KEY` env var, if set, must be sent as `key`.
- **Telling the feeds apart** (checked 2026-10-04): Bet365/Sbobet livegame files are mostly `getData2` rows with a handful of `getData2none`; Bet365 Live is `getData2none` only (and its `tablenext` 404s). So `getData2none` rows alone do NOT identify the Live feed. With no match in play a pre-match book's livegame file has no `getData2` rows at all (2026-10-05: Bet365 = 0 / 1 none), so whenever there are none `probe()` also reads `tablenext/day0` (else day1): upcoming fixtures there = Bet365/Sbobet hash, none = Live feed or a rotated hash. That is what lets a valid hash be saved when nothing is being played.
- **Blackouts:** botbot3 intermittently serves every feed as the empty cookie-notice shell (~3.3 KB, no rows) for ~30-60 s — indistinguishable from a rotated hash by content. `fetchBotbotFile` retries an empty answer once after 1.2 s; `hashes.js` only calls an empty feed stale when another feed has data at the same moment (and Bet365 Live only when ≥3 matches are in play), and refuses to save during a blackout.
- **Self-heal:** `healHashes(env, {book: currentHash}, test)` tries the hash this isolate found earlier, then one discovery round (direct page fetch, else Railway relay), and saves a working replacement to KV — used by `upcoming.js` (empty/404 day0), `livematch.js`, `livescore.js` (Bet365 404, and Bet365 Live empty while ≥3 matches are live) and `GET /api/hashes`. An isolate-discovered hash is only ever a retry, never ahead of the resolved one (it used to beat env vars until a redeploy). Direct discovery from Cloudflare's edge is still WAF-blocked; from other networks the bare `Mozilla/5.0` UA gets through (2026-10-04, after a 403 on the full UA).
- **Railway picks up pasted hashes within `HASH_SYNC_MINUTES` (5)** (added 2026-10-04): `telegram/livescore.js`'s `syncHashesFromApp()` (scheduled by `notify.js`) reads `GET <HASH_RELAY_URL or DATA_URL>/api/hashes?raw=1` — the stored hashes only, one KV read, no feed checks — and adopts a book's KV hash when it differs and was saved after this process last changed that hash itself (start-up constants/env count as older than anything saved), so an older stored value never undoes a hash the bot discovered on its own. Separately, when its own discovery fails, the bot still relays through `/api/livescore`'s `book`/`sbobet_book`/`bet365live_book` fields.

## The Livescore Function (`functions/api/livescore.js`)

Fetches all live/upcoming matches with embedded Pinnacle odds in a single request.

**Bet365 book hash** (the primary/only live book now — see the constant comments in the file) rotates periodically. The code auto-discovers it:
1. Fast path: try `GS_PRIMARY` (`Q`) + stored `BET365_HASH` (1 subrequest)
2. On 404: try direct discovery — fetch `https://www.asianbetsoccer.com/it/livescore.html`, extract new hash from `#book_filter` option values, retry
3. **If direct discovery comes back empty**, relay through Railway instead (`RAILWAY_RELAY_URL` env var + `GET /hashes`) — see below, this is the important path in practice.

**Direct discovery from this Function is effectively always blocked** (confirmed 2026-08-24): asianbetsoccer.com's WAF returns an HTTP 202 bot-challenge (193-byte body) to every request from Cloudflare's edge network, regardless of header set. So step 2 above almost never succeeds on its own — step 3 (the Railway relay) is what actually keeps the hash fresh without manual intervention now.

**Railway relay (`RAILWAY_RELAY_URL`):** `telegram/notify.js` runs an HTTP server (`startHashRelayServer()` in `notify.js`, needs Railway's public networking enabled so `process.env.PORT` is set) exposing `GET /hashes` — the hashes it last discovered via its own direct scrape of asianbetsoccer.com (Railway's outbound IP isn't subject to the Cloudflare-specific WAF block). Set `RAILWAY_RELAY_URL` in the Cloudflare Pages project's env vars to the Railway service's public URL to enable this fallback; `functions/api/livescore.js`'s `fetchHashesViaRailwayRelay()` calls it whenever direct discovery returns nothing. Without it, a stale hash requires a manual `BET365_HASH` env var update (see `?debug=1`'s `hash_discovery` block for diagnostics on which path is failing).

To manually update the hash as a last resort: open DevTools → Network on the asianbetsoccer livescore page, find a request to `botbot3.space/tables/v4/*/livegame/*.js`, copy the 40-char hex filename, and set it as `BET365_HASH` in both the Cloudflare Pages and Railway dashboards.

**Confirmed botbot3.space endpoint:**
```
https://botbot3.space/tables/v4/Q/livegame/{PINNACLE_HASH}.js?date={timestamp}&_={timestamp+1}
```

**JS file format** — builds tables via repeated function calls:
- `match2text += getData2(rowIdx, 1, leagueId, enc, matchId, ah_hc, ah_ho, ...)` — odds data
- `match1text += getDatalive1(...)` — currently live matches (minute like `'5\''` at `[10]`)
- `match1text += getDatalast1(...)` — upcoming/finishing matches (ISO datetime at `[10]`)

**Confirmed `getData2()` param indices:**
```
[4]=matchId  [5]=ah_hc  [6]=ah_ho  [11]=ho_c  [12]=ho_o
[16]=ao_c    [17]=ao_o  [21]=tl_c  [22]=tl_o
[24]=ov_c    [25]=ov_o  [29]=un_c  [30]=un_o
```

**`getDatalive1` / `getDatalast1` confirmed param indices:**
```
[5]=matchId   [6]=leagueName   [9]=homeTeam   [10]=timeOrMinute   [22]=awayTeam
[11]=home goals (integer)      [23]=away goals (integer)
[24]=home corners (integer)    [25]=away corners (integer)
[4]=statusCode — contains match stats like 'Q1_FA3-SB1-FC2' (NOT the score)
```
Score is NOT encoded in the statusCode `FD` pattern (old format). Goals are at args[11]/[23].
Score is only extracted for live matches (those with a minute field); upcoming matches also have 0s there.

**Parsing strategy in `livescore.js`:**
1. `parseGetData2Calls()` — extracts odds from `getData2()` args using confirmed indices
2. `parseGetData1Calls()` — regex matches both `getDatalive1` and `getDatalast1`; extracts teams, league, minute, score (from args[11]/[23])
3. `mergeMatchData()` — merges by `matchId`; falls back to array index
4. `fetchPinnacleHash()` — auto-discovers current Pinnacle hash from asianbetsoccer livescore page
5. HTML string fallback (`parseLivegameTables`) kept for older botbot3 format (jQuery `.html("…")`)

**Returns:**
```json
{ matches: [{ id, url, home_team, away_team, league, minute, score, odds: {ah_hc, ah_ho, ho_c, ho_o, ao_c, ao_o, tl_c, tl_o, ov_c, ov_o, un_c, un_o} }] }
```
`app.js`'s Live Games tab (`pollLiveMatches()`) uses embedded odds directly, skipping per-match `/api/scrape` calls.

**Debug endpoint:** `GET /api/livescore?debug=1` — returns `match_count`, `matches_preview` (all matches), `getData1_parsed` (every getDatalive1 call as a clean arg array) for diagnosing format changes.

## Match Tab (`static/match.js` + `static/fair_model.js`, added 2026-10-02)

The default tab. Paste an asianbetsoccer match link → `/api/scrape` → one page with four views:
- **Overview** — header (league, teams, cards, kick-off countdown / live minute / FT, score, HT, corners, expected goals), Bet365 opening→current movement cards (1X2, AH line+price, TL, Over price), a plain-language movement read with the measured residual effects (see below), and an all-books price table (best price on Bet365's line highlighted).
- **Value** — Bet365 current price vs the reference book's de-vigged fair price: edge %, advised min odds (`fair × (1 + threshold)`), fractional-Kelly stake. Reference = Sbobet when listed (Auto falls back to Crown → market avg, labelled **not backtested**). Same-line AH/O-U rows use the reference book's own de-vigged price ("direct" — the backtested comparison); different-line rows and **all 1X2 rows** use `fair_model.js` fitted to the reference book's AH+TL (tagged `model`). Also shows the opening-vs-opening gap as context.
- **Fair prices** — `FairModel.markets()` for every market (1X2, DC, DNB, BTTS, totals ladder, AH ladder, team totals, specials, correct score, 1H/2H), with Bet365's price + edge where it quotes that exact market. Once the match is live, an **In-play from now** section (another goal, next goal, final result/totals from the current score, uniform remaining-goal share — a coarse model, not `computeLiveOdd`).

## Cross-Fit Bet Selection — winner's-curse fix (`static/app.js`, added 2026-08-26)

`buildQualifyingList`'s argmax over up to ~32 candidate bets (or ~10 for Live Games' 2H set), all scored from the same historical pool, systematically inflates whichever candidate wins ("winner's curse" / multiple-comparison bias) — the pool that makes a bet look best is the same one being asked how good it is. Walk-forward backtested on Live Games' HT pick across 3 held-out months (`telegram/backtest_live_ui_split_sample.js`): picking AND pricing from the same pool loses money at the displayed "min odds" (−22% to −29% ROI) despite a perfectly reasonable ~40-50% hit rate; splitting the historical dataset into two disjoint folds and pricing a candidate with the fold that did **not** select it flips ROI to consistently positive (+4% to +22%) with the hit rate barely moved — confirming the bias is in the *pricing*, not the *pick*.

**Mechanism:** every row gets a stable `fold` ('A'/'B') at load time (`foldOf(date, homeTeam, awayTeam, league)` in `processRow` — a deterministic hash, not per-session random, so the same match always lands in the same fold across reloads). `mergeCrossFit(betsA, betsB)` takes two independently fold-computed `scoreBets()` arrays and keeps a bet key only if it qualifies (`qualifiesBet`) in at least one fold, always pricing it with the *other* fold's numbers (preferring the larger-`n` cross-priced estimate if both folds independently qualify it); survivors are tagged `_pricedFold` so `qualifiesBet` short-circuits true for them (their qualification was already decided by the selecting fold, re-checking the pricing fold's own z/lo would be both redundant and sometimes wrongly negative) and so live-decay dispatch (`buildLiveAdjustedBet`/`buildLive1HAdjustedBet`) knows which fold's anchor map to use for internal same-key lookups (favScored2H/homeScored2H siblings, etc.). `crossFitBets(db, filterRows, minN)` / `computeFoldPair(db, filterRows, minN)` are the entry points — `filterRows(pool)` runs the caller's normal `applyConfig`/`applyBaselineConfig`/`applyGameState` chain on one fold's rows and returns `{ stateRows, baselineRows, baselineSideRows }`.

**Applied to:** Manual Analysis (`analyzeMatch`'s `allBetsQual`/`gsAllBetsQual`, including the minute>45 live-decay branch) and Live Games (`analyzeLiveMatch`'s `preBetsQual`/`gsBetsQual`, both the 1H-live and HT/2H-live branches) — anywhere `buildQualifyingList` picks a Top Pick/Qualifying Bets list. The original un-gated single-pool numbers (`allBets`/`gsAllBets`, `preBets`/`gsBets`) are kept unchanged and still feed **Value Hunting** and the **All Bets dashboard** (`renderBetDashboard`) — those don't do an argmax across candidates, so the bias doesn't apply and they still benefit from seeing every key, not just cross-fit survivors. Internal anchor lookups that aren't themselves argmax candidates (e.g. `analyzeMatch`'s `htAnchorMap` used only for dispatch) are deliberately left on the plain single-pool computation.

**Applied to the Dashboard too (`openingOddsSignal`, added 2026-08-26):** same argmax shape, just over the 13 `_DASHBOARD_BET_KEYS` FT/pre-match markets instead of all 32/10. Since the Dashboard's `scoreBetsFast`/`dashboardBaselineStats` path is specifically optimized to scan hundreds of fixtures fast (see its own header comment), this reuses that caching pattern rather than `crossFitBets`/`computeFoldPair` directly: `_dashBaseCacheFold` (keyed `${favLine}|${favSide}|${fold}`) caches each fold's base pool, `scoreBetsFast` is run once per fold on the same odds-band/TL-cluster-narrowed rows, and the two fold results are merged via the same `mergeCrossFit(betsA, betsB)` used everywhere else. Falls back to the plain single-pool `allBets.filter(qualifiesBet)` if either fold is too thin (`< DEFAULT_MIN_N`) once band-narrowed and halved — a real risk for less common odds bands. Walk-forward backtested (`telegram/backtest_dashboard_split_sample.js`, 3 held-out months): a much smaller effect than Live Games/Manual (fewer candidates in the argmax = less winner's-curse to correct) — TOP+MAJOR control ROI@mo −1.7% to −5.4% → split-sample +0.2% to +3.5% (positive in all 3 months); OTHER-tier control −0.8% to −3.7% → split-sample −2.4% to +0.4% (improved in all 3 months, but stayed net negative in 2 of 3) — OTHER-tier Dashboard picks likely lack real edge beyond the pricing bias, which this fix doesn't manufacture. Applied anyway since it's a strict improvement everywhere tested, just don't expect it to make OTHER-tier Dashboard picks reliably profitable on its own.

**Not yet applied to:** Telegram strategies (L123/LATEGOAL/QUIET2H) — `telegram/engine.js`'s `processRow` stamps the same `fold` field (kept in sync per this file's sync-requirement note) but nothing consumes it yet, since those use a differently-shaped selection path (`l123BestQualifying`, `lateGoalRec`, etc.) — a separate follow-up.

**Cost:** halving the pool per fold means more cells fall under `MIN_N` — coverage (how often a match/fixture gets a qualifying pick at all) drops noticeably (backtested at roughly 5-9% fewer qualifying picks per month for Live Games) in exchange for the ROI fix. Live Games' per-match analysis now runs `scoreBets` roughly 3x more often (once per fold, per stage) than before; the Dashboard runs `scoreBetsFast` roughly 3x more often per unique (fav_line, fav_side, odds band, TL cluster) combo, not per fixture, so the added cost scales with how many distinct combos actually occur in a given fixture window, not with fixture count directly.

## Dashboard Near-Kickoff Movement Signal (`static/app.js`, added 2026-08-27, revised 2026-08-28)

The Daily Dashboard's per-fixture pick (`analyzeFixtureForDashboard`) is opening-odds-only by design (`deriveOpeningContext`'s header comment) for most of its window. For fixtures within `NEAR_KICKOFF_MIN` (30 min, the Dashboard's own narrowest window option) of kickoff, the headline pick switches to **Layer 2 (movement) standalone** — `movementSignal(moveCfg)`, fed a `buildCfgFromLiveOdds`-built cfg from the live feed's current odds — replacing `sig1`'s opening-only pick. `qualifies` is forced true when a movement pick exists (movement never surfaces a non-qualifying pick — no fallback branch, unlike Layer 1); the fixture's tier then falls through the normal `sig2`/`sig3`-based scoring, same as the opening-odds-only path. The result's `l2` field (the raw bet object, or `null`) is surfaced in the UI as a `📈 Near-kickoff — movement (Layer 2) signal` line; fixtures outside the window, or where movement doesn't qualify, fall back to the original opening-odds-only scoring unchanged.

**Why 30 min:** the live feed's "current" odds field is only a meaningful proxy for something close to the true closing line inside a narrow pre-kickoff window — at the Dashboard's wider windows (1h/4h/8h/24h) it's just an early snapshot that can still move a lot before real kickoff. 30 min is a conservative compromise, not derived from any specific validated horizon.

**History — originally a 3-layer L123-style consensus (2026-08-27), replaced with movement-only (2026-08-28):** the first version of this feature ran the full L123 consensus here (Layer 1 opening + Layer 2 movement + Layer 3 closing/current odds, mirroring `telegram/notify.js`'s Strategy L123 — headline bet only replaced when ≥2/3 layers agreed), both cross-fit corrected the same way `openingOddsSignal` is (`computeFoldPair`/`mergeCrossFit`, same fold-split fix used everywhere else). Walk-forward backtested against **real Bet365 closing prices** (not just historical hit rate) across 19 held-out months (`telegram/backtest_l123_consensus_pricing.js`, `backtest_l2_by_favline.js`, `backtest_tl25_over_under.js`, `backtest_1x2_bookmaker_check.js`):

- The 3-layer consensus showed **no reliable edge vs. real market prices** — pooled ROI negative in both TOP+MAJOR (4 months, n=105 checkable) and OTHER tier (4 months, n=1,028 checkable; OTHER was *worse* than TOP+MAJOR, contradicting the "less liquid market = easier edge" intuition — `-3.8pp` avg edge vs. market vs. TOP+MAJOR's `+1.8pp`).
- Averaging the agreeing layers' `p`/`lo` (`averageAgreeingBet`, the interim pricing fix) and prioritizing Layer 3 (closing odds) both underperformed the original "first agreeing layer" pricing on real-market ROI — Layer 3 specifically was the weakest of the three, plausibly because its signal converges toward what the market has already priced in.
- **Layer 2 (movement) standalone**, tested independently of the consensus requirement, showed a real, walk-forward-consistent edge in a specific slice: **Over/Under 2.5 FT at closing TL 2.5-3**, especially once gated on the real bookmaker price clearing the app's own conservative min-odds (`mo_lo`) — **edge vs. market positive in 19/19 held-out months** (the only result in this whole investigation with that consistency), and **+10% pooled ROI** on the `mo_lo`-gated subset (n=276 of 1,147 checkable picks, 24.1% actually clearable at a real price). The 1X2 (Home/Draw/Away) market showed a similar-looking pooled number (+8.0%) but wasn't internally consistent (Away win alone driving it, Home win and Draw both negative) — treated as unconfirmed, not used to justify this change.

`l123ConsensusSignal`, `closingOddsSignal` (Layer 3), and `averageAgreeingBet` were all removed as dead code once nothing called them (only `analyzeFixtureForDashboard` used them, and only for the now-replaced consensus path). `movementSignal` (Layer 2, cross-fit corrected) is unchanged and is what the Dashboard now calls directly.

**Not enforced in code — the gate that actually made this profitable in backtest is the mo_lo comparison itself**, which happens implicitly: the UI shows `bet.mo`/`bet.mo_lo` as the min-odds the user needs, and the backtested edge only showed up when the *real* bookmaker price cleared `mo_lo` specifically (not just `mo`) — so treat the near-kickoff movement pick as most trustworthy when the live price you can actually get is well above the displayed conservative figure, not just above the fair-odds one.

## Live Games Tab (`static/app.js`)

Auto-scans in-play matches from `/api/livescore` and scores each one against the historical dataset using **the match's own real closing-odds signal pattern** (`buildCfgFromLiveOdds` — same cfg-building function the old `checkLiveBets` used) — not a hypothetical signal sweep (`discover()` stays unwired/out of scope for this tab).

- `fetchLiveMatches()` — hits `/api/livescore`, keeps only `data.matches` entries with `minute != null` (the live/in-play ones; `next_matches` and not-yet-started `matches` entries are excluded, unlike the Dashboard's `fetchUpcomingFixtures`).
- **HT auto-snapshot**: `updateHtAnchor(match, minute)` captures `match.score` as the HT anchor the first time a match is seen with a minute in the 44–50 window (or the `'HT'` sentinel) — no manual entry needed. Anchors are kept in `_liveHtAnchors` (`Map<matchId, {home, away, ts}>`) and persisted to `localStorage['halvest_ht_anchors']`, pruned of entries older than `HT_ANCHOR_MAX_AGE_MS` (6h) on load. A match first observed after minute 50 with no prior anchor is flagged `anchorStatus: 'unknown'` and only gets closing-odds/pre-match bets, never live 2H decay, until a fresh anchor is captured (impossible for that match instance).
- `analyzeLiveMatch(match, minute)` — runs `applyConfig`/`applyBaselineConfig` + `scoreBets` for the pre-match pool (`preBets`, always computed if enough history), then, once an HT anchor is known, `applyGameState({trigger:'HT',...})` + `scoreBets` for the HT-conditioned pool (`htBets`), then — once `minute > 45` and a current score is available — `buildLiveAdjustedBet` per bet (goals-since-anchor derived from `match.score − anchor`, mapped to fav/dog via `cfg.fav_side`) for the minute-decayed live pool (`liveBets`). Whichever of `liveBets`/`htBets`/`preBets` is most specific becomes `gsBets`, consumed the same way Manual Analysis's `gsAllBets` is.
- `pollLiveMatches()` — fetches, snapshots anchors, analyzes, ranks matches by their best bet's CI-adjusted score (`rankScore` = `z * lo/100`, same metric `scoreBets` itself sorts by), renders. Runs immediately on entering the tab and every `LIVE_POLL_MS` (60s) via `setInterval` while the tab stays active and auto-refresh is on (`toggleLiveAutoRefresh`) — the only recurring timer in this codebase.
- **Opportunities feed (redesigned 2026-09-05, replacing the old Focus/All-markets mode toggle)**: the tab now leads with a single ranked list, not a mode choice. `collectAllQualifyingLiveBets(_liveMatches)` sweeps every "ok" match's `preBetsQual`/`gsBetsQual` (all ~10 home/away/total markets `filterLiveScanBets` allows Live Games to see, not just the 7 `FOCUS_MARKET_BETS`) via `buildQualifyingList`, pools every qualifying bet across every match into one array, and sorts by `liveEdgeScore(bet)` = `bet.lo - bet.bl` — the Wilson-CI-lower-bound edge over baseline, in pp (literally the number already shown as "✓ lo clears baseline by Xpp"). Deliberately **not** `rankScore` (`z * lo/100`, used everywhere else in the app to pick the single best bet *within* one match/config): `rankScore`'s `lo/100` term rewards a bet just for having a high raw probability (e.g. a heavy favourite's win market) regardless of how thin its margin over baseline is — the wrong thing to lead with when comparing bets across many different matches and market types at once, which is exactly what this cross-match feed does. `lo - bl` is already sample-size-aware without needing `n` as a separate ranking input (small `n` → wide CI → `lo` sits far below the point estimate → margin shrinks; large `n` → narrow CI → `lo` converges on the point estimate), so `n` is shown as a supporting `sampleBadge`, not folded into the sort key. Rendered as the "🎯 OPPORTUNITIES" section via `renderQualifyingLiveBetRow(entry, {top, qualifies})`, headlined by `bet.mo_lo` (the conservative min odds — `renderBetPickBlock(bet, qualifies, 'mo_lo')`) since that's literally "the min odds to consider in order to bet" the feature was redesigned to answer directly, not the winner's-curse-prone fair odds (`mo`) shown elsewhere by default. The single best row is tagged `top:true` for a "🏆 BEST OPPORTUNITY RIGHT NOW" marker. If nothing qualifies anywhere, `collectAllValueHuntLiveBets` falls back to the best positive-edge-but-not-yet-confident bet per match (`buildValueHuntList`), same `liveEdgeScore` sort, rendered the same way but tagged `qualifies:false` (◆ VALUE HUNT styling) so the feed never goes blank, it just gets clearer about confidence.
- `renderLiveGames()` — the Opportunities feed (see above) followed by "ALL LIVE MATCHES": one simplified `.scan-card` per match (`renderLiveMatchCard`) showing just team names, live score/minute, and that match's own single best bet (qualifying bet if one exists, else its own value-hunt bet, still picked via `pickLiveBetForCard`'s `rankScore`-based internal choice — only the cross-match *list order* uses `liveEdgeScore`) headlined the same way by `mo_lo` plus a sample badge — no per-card 1T/2T panel or beta-model ladder anymore, those live in the detail modal only, one click away (`openLiveMatchDetail(idx)` — index into `_liveMatches`, deliberately **not** a team-name-derived id, since team/league names come from the scraped feed and aren't safe to embed raw into an inline `onclick`).
- **Max-odds cap (added 2026-09-05 at the user's request — "do not put the bet where odds is too big, like 4 or more")**: `state.liveMaxOdds` (`LIVE_MAX_ODDS_PRESETS` — `null`/ALL, 3, 4 default, 6; `setLiveMaxOdds()`) excludes any bet whose `mo_lo` exceeds the cap from being surfaced as THE pick — a long-odds bet is a rare, thin-probability historical event, worse to lead with regardless of how wide its baseline margin looks. `passesMaxOdds(bet)` is the shared check; `pickLiveBetForCard(analysis)` (shared by `topLiveBet()` and `renderLiveMatchCard`'s own preview, so both surfaces always agree) walks the qualifying list then the value-hunt list and returns the first bet clearing the cap, and `collectAllQualifyingLiveBets`/`collectAllValueHuntLiveBets` apply the same filter per-entry (a match can still contribute a different, lower-odds qualifying bet even if its best-by-edge one is capped out). This is a bet-level filter, not a match-level one (unlike league tier/minute band) — a match with only long-odds bets just shows "no bet clears the bar" rather than being hidden outright, and the filter never touches the detail modal (`openLiveMatchDetail`), which always shows every qualifying bet unfiltered. Session-only, not persisted, consistent with `liveTierFilter`/`liveMinuteBand`.
- `openLiveMatchDetail(idx)` opens `#live-match-modal` (`.modal-overlay`/`.modal-box` CSS) showing the full per-match breakdown — cfg summary, the 1T/2T Focus panel (`renderFocusMarketsPanel`, always shown now — the old `state.liveUiMode==='focus'` gate is gone), the beta pricing panel (still gated on `state.useNewLiveModel`), Top Pick + every qualifying bet for this match (reuses `renderMergedBetCard`/`renderTopValueBanner` unchanged), all always-visible; the rarely-needed raw data (full Value Hunt list, `buildTraceHtml` filter trace, `renderBetDashboard`'s every-market table) is collapsed behind one "▸ Full data (every market, filter trace)" `<details>` so the modal itself stays scannable too. Rank namespace `'live-detail-*'`.
- **Kelly-widget rank namespacing**: `buildBetCol` keys `_lastBetsByWidget` by `${rank}-${colId}`, and this map is shared globally (reset only by `renderMatchResults`, i.e. Manual Analysis runs). Live Games' banner and modal use the `'live-top'`/`'live-detail-*'` rank prefixes specifically to avoid colliding with Manual Analysis's own `'top'`/numeric ranks when both are present in the DOM (the modal layers over whichever tab is active).
- **Closing TL clustered, not exact-matched (added 2026-08-28)**: `buildRawCfgFromLiveOdds` used to set `cfg.tl_c` to the match's exact closing TL, which `applyConfig`/`applyBaselineConfig` then matched within ±0.13 — a needlessly narrow filter, since (unlike `fav_line`, which is genuinely quoted at fixed 0.25 steps) TL isn't naturally discretized this tightly. Now also sets `cfg.tl_cluster` to the matching `TL_CLUSTERS` band (`<2`/`2-2.5`/`2.5-3`/`>3`, the same bands the Dashboard already uses), which `applyConfig`/`applyBaselineConfig`/`traceConfig` already gave priority over exact `tl_c` (see their "TL exact range takes priority over cluster and exact tl_c" branch — this was previously unused by Live Games since only `tl_c` was ever set). `tl_c` itself is kept in the cfg object for display only (the `cfg-summary` line in the match-detail modal still shows the exact value). This both grows Live Games' typically-small historical pools (see the sample-size discussion this was motivated by) and keeps TL 2.5-3 matches grouped together — the one band walk-forward testing found a real, 19/19-months-consistent edge in for the Dashboard's movement signal (see "Dashboard Near-Kickoff Movement Signal" below); the match's own exact HT scoreline (`applyGameState`) was deliberately left un-clustered, since that's untested territory — see that section for why.

## The Scrape Function (`functions/api/scrape.js`)

Accepts `GET /api/scrape?url=<asianbetsoccer.com/match?id=HEX>`. Strategy:

1. Extracts the `?id=` hex from the asianbetsoccer URL.
2. Fetches `https://botbot3.space/tables/v4/oddsComp/<id>.js` server-side (CORS bypass).
3. Parses `tablematch1` to find each bookmaker's index. **Bet365 is tried first** (the bundled historical dataset is Bet365-sourced, so analysis is calibrated against it); falls back to Pinnacle only if Bet365 isn't listed or fails to parse. Previously a match with no Pinnacle odds errored out even when Bet365 was available.
4. Parses `tablematch2`, splits groups by `<tr class='vrng'>` separator rows, extracts the chosen book's group.
5. Parses H/A rows **by TD cell position** (not CSS class — classes like `SU`/`SD`/`SN` vary per match).

Returns JSON: `ah_hc`, `ah_ho`, `ho_c`, `ho_o`, `ao_c`, `ao_o`, `tl_c`, `tl_o`, `ov_c`, `ov_o`, `un_c`, `un_o` — mapped directly to app input fields. `static/app.js`'s reference-odds display shows whichever book *wasn't* used for the primary fields, labeled accordingly.

**If the source HTML structure changes**, update positional offsets in `parseTds` (lines ~164–180 of `scrape.js`).

## Live 2H Time-Decay Odds (`computeLiveOdd` in `static/app.js`)

Estimates a live fair probability/odd for 2H-only bets given HT hit%, match minute, and current 2H score. Recalibrated (2026-08-21) against this app's own ~165k-match dataset:
- **Score-state modifier** is now three bet-class-specific tables derived from the app's own data (previously backwards — it boosted the *trailing* team instead of the already-leading favourite).
- **Intra-half timing curve** was sourced from external published goal-timing research and gated behind a flat-decay toggle, since it couldn't be validated against this dataset (no goal-minute data, only HT/FT scores) — see the next paragraph, this blocker is now closed.
- Fixed a bug where the function returned `live_p:100` whenever time ran out, regardless of whether the bet had actually hit.

**Updated 2026-08-22, validated against real goal-minute data** (`football-data/data/goals_time2` via `telegram/goal_timing.js`, 12 domestic leagues × 3 seasons × 27,321 goals):
- **`_1H_INTENSITY`/`_2H_INTENSITY`** (the intra-half timing curve) replaced with the real empirical shape — the old externally-sourced curve significantly overstated 1st-half late-game clustering and got the 2nd half's 15-30-minute bucket's direction backwards (assumed elevated, real data shows it's the *lowest* of the three buckets). Cross-league standard deviation was small (0.03-0.05) despite very different leagues, so a single pooled curve is used (`computeLiveOdd` has no league parameter — see `static/data/goal_timing_summary.json` for the per-league breakdown if this is revisited).
- **`_TOTAL_SCORE_MOD`** replaced with real data too — this table is a genuine apples-to-apples fix (total goals don't care which side is the favourite, only the margin's magnitude, so goals_time2's home/away-only data measures it directly). Real total 2H scoring barely responds to the current margin (leading team's own scoring rises ~27% at a 2+ margin, trailing team's falls ~23%, nearly cancelling out — net +2.6%, not the +30% previously assumed).
- **`_FAV_SCORE_MOD`/`_DOG_SCORE_MOD` left unchanged** — goals_time2 has no pre-match favourite designation, only home/away, so it can't isolate a favourite-specific effect from a generic leading/trailing-team effect. A generic leading/trailing re-derivation found the "leading" side's pattern roughly consistent with the existing tables, but a real divergence on the "trailing favourite" entries — generic trailing teams score progressively *less* as the margin grows (0.99/0.95/0.77 at margin 0/1/2+), not the flat-to-mild-increase the table assumes for a trailing favourite specifically. Plausibly explained by favourites retaining more quality when behind than a generic trailing team, but unverifiable without linking to pre-match odds — treat the "-1"/"-2" (favourite trailing) entries with more caution than "1"/"2" (favourite leading).

**1H live-decay added (2026-08-26)** — previously 1H bets in Live Games only ever showed the static pre-match/closing-odds hit rate, with no minute-by-minute updating (the `_1H_INTENSITY` curve above was calibrated but never wired into any live-decay call). `computeLive1HOdd`/`computeLiveResult1H`/`computeLiveBtts1H`/`buildLive1HAdjustedBet` mirror the 2H functions, anchored at kickoff (always 0-0, so no anchor-capture step is needed the way 2H needs an HT snapshot) instead of HT. Deliberately has **no score-state margin modifier** — the `_FAV_SCORE_MOD`/`_DOG_SCORE_MOD`/`_TOTAL_SCORE_MOD` tables above are calibrated from *HT-margin → rest-of-2H* scoring, a different question than *current-1H-margin → rest-of-1H* scoring that was never measured; applying them here would misrepresent an untested relationship. Not ported to `telegram/live_odds.js` (Telegram's LATEGOAL/QUIET2H strategies are 2H-only by design) — web UI only.

**`_IT_1H`/`_IT_2H` calibrated from data (2026-08-26)**, replacing assumed values (2 and 4 respectively — `_IT_1H` was previously just "half of `_IT_2H`", and `_IT_2H` itself was never calibrated). Each represents how many extra minutes of goal-intensity the stoppage-time window adds, in this model's own rate-integral terms; solved so that mass's share of the whole half matches the real share of goals recorded during that half's actual stoppage time (`45+N'`/`90+N'` incident minutes) in `goals_time2` (12 leagues × 3 seasons through 2024-2025): 1H — n=12,261 first-half goals, 5.81% in recorded 1H stoppage (avg 2.65 added min when it happens) → **`_IT_1H` = 2.40**. 2H — n=15,060 second-half goals, 12.32% in recorded 2H stoppage (avg 3.72 added min) → **`_IT_2H` = 5.07**. The 2H stoppage share running ~2× the 1H share matches the general refereeing pattern (more subs/treatment/VAR stoppages accumulate by full time) — a sanity check the calibration passes, not something it was tuned to hit. Mirrored into `telegram/live_odds.js`'s `_IT_2H`.

**`mo_lo` staleness fix (2026-08-28):** the live-decay bet objects returned by `buildLiveAdjustedBet` (2H, 3 branches — result/BTTS/generic) and `buildLive1HAdjustedBet` (1H, same 3 branches) each spread `...anchorBet` and correctly recompute `p`/`lo`/`mo`/`mo_mid` from the decayed probabilities, but were **not** recomputing `mo_lo` — it silently kept the anchor bet's pre-decay value (the HT-conditioned, but not minute-decayed, conservative odds) in all 6 return sites. Harmless while nothing read `bet.mo_lo` for a live-decayed pick, but a real correctness gap once `mo_lo` started being relied on elsewhere (see the Dashboard's near-kickoff movement pick above, which now displays `mo_lo` specifically because it's the number that backtested profitable). All 6 sites now also set `mo_lo: minOdds(lo)`, consistent with `mo`/`mo_mid`.

## Telegram Notifier (`telegram/`)

Standalone Node.js service that polls live matches and sends Telegram alerts under three active strategies — **L123** (pre-match), **LATEGOAL** (in-play, still no 2H goal), and **QUIET2H** (in-play, expect a quiet 2nd half; see below); everything else is legacy (see further down). Deployable to Railway or run locally.

```bash
cd telegram
npm install

node notify.js          # start scheduler (runs every SCAN_INTERVAL_MINUTES, default 2 min)
node notify.js --once   # single scan + exit (for testing)
node tune_l123.js       # walk-forward validator for the L123 qualifying gate (Wilson CI vs point estimate)
node layer_analysis.js  # convergence study — which layer-agreement bucket (1/3, 2/3, 3/3) has the best hit%/ROI
```

**Strategy L123 — Layer 1/2/3 consensus** (`notify.js` + `config.js`): three independent layers each independently recommend a bet from historical data, each restricted to only the information that layer is allowed to see:
- **Layer 1 — opening odds only** (fav opening odds band + opening TL band)
- **Layer 2 — movement only** (`line_move`, fav/dog odds move, `tl_move`)
- **Layer 3 — closing odds only** (fav closing odds band + closing TL band)

An alert fires in the **10-minute pre-match window** (kickoff minus 10 minutes down to kickoff itself — see `PRE_MATCH_WINDOW_MIN` in `notify.js`'s `matchContext()`) once `L123_MIN_AGREE` (default 2) of the 3 layers independently land on the same bet, using odds polled every `SCAN_INTERVAL_MINUTES`. Pre-match rather than in-play by design — it gives time to actually place the bet at a stable price instead of needing fast in-play execution once the match has started. This came out of `layer_analysis.js`'s convergence study, which found the "2/3 agree" and "3/3 agree" buckets beat any single layer alone or matches where layers disagree.

Note this pre-match timing is a real shift from how L123 was originally walk-forward validated (see the ROI numbers below) — Layer 3 ("closing odds only") was validated against the true closing line *at* kickoff, and odds polled up to 10 minutes early can still move before then, so it's a same-idea-different-timing approximation of "closing," not the exact thing the walk-forward backtest measured.

**Qualifying gate (walk-forward validated 2026-08-21):** bets qualify off the **Wilson CI lower bound**, not the raw point estimate — `(b.lo - b.bl) >= L123_MIN_EDGE`, plus `n >= L123_MIN_N`, `z >= L123_MIN_Z`, baseline `>= L123_MIN_BASELINE` — per layer. The prior point-estimate gate produced negative-to-flat ROI@fair OOS despite good-looking hit rates (winner's-curse selection from sweeping thousands of cells). Gating on the CI lower bound instead: **+7.3% ROI@fair** pooled across 5 exploratory held-out months (5/5 positive), **+10.6%** across 2 never-touched lock-box months (2/2 positive). `telegram/tune_l123.js` is the reusable validator.

| `L123_ENABLED` | `false` | Switched off in code 2026-10-04 (user request) — the env var is ignored; restore `process.env.L123_ENABLED === 'true'` in config.js to bring it back |
| `L123_TIER` | `TOP+MAJOR` | League tier filter (falls back to `LEAGUE_TIER`) |
| `L123_MIN_N` | 30 | Min historical pool size per layer |
| `L123_MIN_Z` | 1.8 | Min z-score per layer |

**Live price gate:** before alerting, the recommended bet's Bet365 live price is checked against the conservative min odds (`bet.mo_lo`, derived from the Wilson CI) — the alert only fires if the live price is at or above it.

**Model probability line (`modelProbLine()`, `notify.js`):** every alert (L123, LATEGOAL, QUIET2H) always prints a standalone `🎲 Model probability (for manual Kelly): X%` line, independent of whether a verified price was found (unlike `kellyLine()`, which only prints once `actualPrice` is known) — so there's always a number to plug into a manual Kelly calculation (e.g. against a different bookmaker's price than the one auto-checked). It's the same CI-lower-bound probability `kellyLine()` itself sizes against — `bet.lo` for L123, the CI-lower live-decayed rate (`liveOddLo.live_p`) for LATEGOAL/QUIET2H — never the raw point-estimate historical rate shown in the "📊 x% historically" line, which is winner's-curse-inflated and would overstake if fed into Kelly directly.

**Data source:** the historical pool is `static/data/Bet365/*.csv` (Bet365-priced, matching the live `match.bet365_odds` it's compared against) — see `DATA_URL`/`DATA_DIR` in `config.js`.

**Architecture:** `notify.js` orchestrates — it calls `engine.js` (port of `app.js` analysis logic) and `livescore.js` (live match + odds fetcher, Bet365 is the primary book — see below). Config lives entirely in `telegram/config.js`.

**Deduplication in `notify.js`:** in-memory `_notified`/`l123Dedup` map keyed by `matchId:betKey`, expires after 2 hours. Resets on process restart — a restarted notifier will re-alert for active matches.

**Sync requirement:** `telegram/engine.js` is a direct port of `static/app.js` constants + engine sections. When changing scoring logic, filter modes, the bet set, or league tier classification in `app.js`, mirror those changes in `telegram/engine.js`.

**Railway deployment:** set `TELEGRAM_TOKEN`, `TELEGRAM_CHAT_ID`, `DATA_URL` as env vars in the Railway dashboard. Also supports `BET365_HASH`/`PINNACLE_HASH`/`SBOBET_HASH` overrides as a no-redeploy manual stopgap if hash auto-discovery breaks (e.g. asianbetsoccer.com's WAF blocking Railway's outbound IP — auto-discovery failures now log the real fetch error instead of swallowing it in a bare `catch{}`). The `railway.json` in `telegram/` defines the start command.

**Enable Railway public networking** so `startHashRelayServer()` in `notify.js` can bind to the auto-assigned `PORT` and serve `GET /hashes` — this is what lets `functions/api/livescore.js` (the web UI, whose own hash discovery is blocked by asianbetsoccer's WAF from Cloudflare's edge — see "The Livescore Function" above) self-heal without a manual `BET365_HASH` paste. Then set `RAILWAY_RELAY_URL` in the Cloudflare Pages project's env vars to the Railway service's public URL.

**Headless-browser hash discovery (added 2026-08-26):** the two-sided relay above has a failure mode — if asianbetsoccer.com's WAF is blocking *both* Cloudflare's edge fetch and Railway's own direct fetch at the same time (confirmed happened 2026-08-26: Railway's discovery, previously only "intermittently" blocked, started failing consistently too), the relay just bounces the same stale hash back and forth between the two sides forever with no real rediscovery happening — nothing in the code flagged this, since a relay "succeeding" (HTTP 200) looks identical whether it returned a fresh hash or an old one. `telegram/livescore.js`'s `fetchAllBookHashes()` now tries a third path in between the direct fetch and the Cloudflare relay: `fetchAllBookHashesViaBrowser()` drives a real headless Chromium (Playwright) to the livescore page and reads `#book_filter` the same way a normal visitor's browser would, which a plain `fetch()` can never replicate. This requires the `playwright` npm dependency and Chromium's system libraries, so `telegram/railway.json` now builds from `telegram/Dockerfile` (`mcr.microsoft.com/playwright:v1.47.2-jammy` base image, which ships Chromium pre-installed matching the pinned `playwright` version — keep both in sync on upgrade) instead of Railway's default Nixpacks builder. Silently skipped (falls through to the Cloudflare relay) if `playwright` isn't installed, so this doesn't break running `notify.js` locally without it. **Caveat:** if the block is IP/ASN-reputation-based rather than a JS challenge, running Chromium from the same Railway network won't help — this path specifically targets the failure mode where asianbetsoccer needs real JS execution to pass (the `202` → `/.well-known/sgcaptcha/` redirect seen on Cloudflare's edge), not an outright IP ban.

**Stale-hash heuristic (added 2026-09-06, `telegram/livescore.js`'s `checkStaleHashHeuristic`):** every rediscovery trigger above (in `tryCombo`/`tryNextCombo`) is gated strictly on a real HTTP 404. In practice botbot3.space keeps serving HTTP 200 with an empty payload (0 `getData2()` calls) for a rotated-out hash for hours before it finally starts 404ing it — during that window every scan just logged "no matches" and did nothing, which was the actual root cause of hash auto-discovery taking hours to catch Bet365's daily rotation instead of minutes. Fix: `fetchNextMatches`'s upcoming-fixtures listing (day0, every league worldwide) coming back genuinely empty is a much stronger stale-hash signal than `fetchLiveMatches` being empty (a quiet period with zero live matches anywhere is normal; zero *upcoming* fixtures anywhere in the world for several consecutive scans essentially never happens with a healthy hash). `notify.js`'s `fetchMatches()` now feeds that "empty-but-not-404" signal to `checkStaleHashHeuristic()` every scan; once it streaks for `NEXTGAME_EMPTY_STREAK_THRESHOLD` (3) consecutive scans (~6 min at the default 2-min interval), it forces a full `fetchAllBookHashes()` rediscovery (same direct→browser→relay chain as the 404 path) regardless of whether botbot3.space has actually 404'd yet, and `fetchMatches()` retries the same scan cycle if a new hash was found. The streak resets on any non-empty result, and also resets after forcing (so a freshly discovered hash gets its own streak before being force-rediscovered again if it also turns out stale).

**Strategy LIVEMODEL — shadow recorder, never alerts** (`livemodel.js` + `notify.js`'s `runLiveGapScan` + config `LIVEMODEL_*`, added 2026-10-07, user idea): Bet365's **in-play** price (the Bet365 Live feed LIVEGAP reads) against the result distribution of similar historical matches. Similar = Bet365 dataset rows with the same pre-match closing favourite line + side and closing-TL band (`line+TL`; just `line` when the band has < 300 rows). The dataset has only HT/FT scores, so the live state is matched by weighting: in the 1st half at minute m with score h-a, each row is weighted by the binomial chance that exactly h / a of its 1st-half goals had happened by m (each goal before m with probability 1 − r, r = `remainingShare` — the goals_time2 intensity curve + stoppage mass, same constants as `live_odds.js`); from HT only rows with the same HT score, weighted the same way on their 2nd-half goals. Remaining goals → final-score distribution → every market Bet365 quotes in play priced as it settles (1X2 final score, AH goals from now, goal line FT total, quarter lines split): model fair odds, edge at Bet365's price, its standard error from the effective number of rows (`neff`, ≥ 40 to price), and Pinnacle's same-line de-vigged fair when paired. Logged to `telegram/data/livemodel/*.jsonl`: a side with edge ≥ `LIVEMODEL_RECORD_MIN_PCT` (3) when it first gets there, when Bet365's price or the fair (> 2%) moves, else every 5 min; every other side every 15 min (calibration). Settled exactly like LIVEGAP (`livegap_result.js`: own pending queue, same blackout-safe gone logic, restart recovery, one match-page read shared by both queues). `node livemodel_report.js` or `GET <bot>/livemodel/report`: calibration (actual ROI per model-edge bucket — matches the model's edge if it is right), first bet per match at ≥3/5/10% (any price, 1.70–2.50, edge − 1 s.e., 1st half vs HT/2H, Pinnacle also above fair), and how often Pinnacle agrees. First live dry run (2026-10-07, 43 matches with Bet365 live, 272 sides): median edge −6.1% (≈ Bet365's in-play margin — the model is roughly level with the market on average), but 32 sides ≥ 5% and 18 ≥ 10%, the biggest where Bet365's line implied far fewer goals than similar matches (e.g. 1-0 at 27', pre-match TL 2.25, live goal line 1.75) — information the model doesn't have (red cards, line-ups, pressure) is the likely cause; the recorder exists to measure that. **Alerts since 2026-10-08** (`LIVEMODEL_ALERTS`, on; user request): one Telegram alert per match (6-h dedup, in memory) for the first side passing `alertBlock` — edge ≥ `LIVEMODEL_MIN_EDGE_PCT` (5) and still ≥ it after one standard error (`LIVEMODEL_USE_SE`), not in the `LIVEMODEL_SKIP_FROM_PCT`–`_TO_PCT` band (10–20%: it lost in every window while 5–10% and ≥ 20% paid), Bet365 `LIVEMODEL_MIN_ODDS`–`_MAX_ODDS` (1.70–2.50), minute ≤ `LIVEMODEL_MAX_MINUTE` (85). Message (`formatAlert`, LIVEGAP's action-first layout): bet as Bet365's in-play market, **BET AT** the lowest price that still clears the threshold + s.e. (`minPrice`: A·q + B ≥ 1 + edge, exact on quarter lines), ⅛-Kelly stake (`LIVEMODEL_KELLY_FRACTION`, € with `LIVEMODEL_BANKROLL`), edge ± s.e., ~N similar matches, Pinnacle's fair when paired. Every alert sent is logged as an `alert` line; the report's ALERTS SENT section settles them at the price shown and at the minimum. The rule comes from the first ~2 days of recordings (≈70 settled first bets, +17–22%) — far too few to call it proven; it fires on most live matches (≈ 90% of matches had a qualifying side). Only runs while `LIVEGAP_ENABLED` (same scan). Tests: `test_livemodel.js`.

**Strategy CROSSMARKET — shadow recorder, never alerts** (`crossmarket.js` + `notify.js`'s `runPriceGapScan` + config `CROSSMARKET_*`, added 2026-10-08): Bet365 priced against Bet365's own other markets, on **same-moment** pre-match prices from the tablenext files the PRICEGAP scan already reads (no extra requests; every Bet365 fixture, not only Sbobet-paired ones). **A** = each 1X2 side vs the 1X2 implied by Bet365's AH + goal line (`FairModel.solve`, two-way de-vig); **B** = each AH side at Bet365's line vs the AH implied by Bet365's 1X2 (power de-vig) + goal line (`FairModel.solveFrom1x2`), exact expected return on quarter lines. Per side it also records whether both markets are still at their opening prices (`un`) and whether the other market moved toward the side while this one followed < half (`lag`, from home−away fair-probability moves since opening). Logged to `telegram/data/crossmarket/*.jsonl`: sides ≥ `CROSSMARKET_RECORD_MIN_PCT` (3) when first seen / when the price or fair (> 1%) moves / hourly, every side every 6 h, and every side once in the last 30 min before kick-off (`cl`, the closing snapshot). Settled on confirmed FT scores via `livegap_result.settleDue` (queue entries keyed on kick-off, checked from KO + 1 h 50, `recoverPending` after a restart). `node crossmarket_report.js` or `GET <bot>/crossmarket/report`: per type and edge ≥ 3/5/8/12% — first sighting, first sighting at opening, closing, closing+lagged (one bet per fixture) — plus calibration of the closing snapshots. **Why:** `telegram/backtest_crossmarket.js` (20 months, 251k matches) found B at the closing price ≥ 5% → +9.2% (17/20 months; lagged +18.7%, 18/18) and A at the opening price ≥ 5% → +13.7% (20/20), against controls of −4.5% (AH) / −11.8% (1X2). But the direction flips (A pays at opening and loses at closing; B pays at closing and loses at opening) — what a dataset recording the 1X2 at a different moment from the AH would produce. Checks found no in-play leakage (the 1X2's extra information shows mostly in the 2nd half; finished match pages carry pre-match 1X2), normal 4-6% AH margins on the winners, and the effect in big leagues too — but the dataset has no per-market timestamps, so only same-moment prices can decide. Tests: `test_crossmarket.js` (also checks that `telegram/fair_model.js` — the bot's copy, since Railway builds `telegram/` alone and `../static/` is not in the image — still matches `static/fair_model.js`; copy it again, keeping its header, after changing the app's).

**Strategy LATEGOAL — "still no 2H goal" watch** (`notify.js` + `config.js`, added 2026-08-22): fires once per match within `LATEGOAL_TRIGGER_WINDOW` (default 68'-72', windowed rather than a single minute so a missed/delayed scan cycle can't fire it arbitrarily late) if the match's HT scoreline historically supports a 2nd-half goal (checked against a fav-line/side + exact-HT-state historical bucket, further split by the match's own closing **Total Line band** — see below) AND no goal has actually been scored since HT (an in-memory HT-score snapshot, captured for every live match crossing minute 44-50 regardless of strategy, is compared against the current score). Considers `over05_2H`/`favScored2H`/`homeScored2H`/`awayScored2H` (`LATEGOAL_BETS`).

**TL-band filter (added 2026-08-23):** the historical pool is bucketed by the match's own closing TL (`TL_BANDS`, same 4 buckets L123's `layer1Live`/`layer3Live` use), falling back to the TL-blind pool if the band is unknown or has fewer than `LATEGOAL_MIN_N` rows. Two identical HT scorelines mean very different things depending on how much of the pre-match total-goals expectation is already "used up" — e.g. HT 0-0 with TL 3.5 vs. HT 0-0 with TL 1.5 — and pooling them together was diluting the signal (`over05_2H` at HT 0-0 ranged 71%-83% across TL bands vs. a flat 75.4% from the TL-blind pool). Walk-forward re-check after adding the band: 1.9pp claimed-vs-actual gap (vs. 2.5pp before), while surfacing more distinct qualifying cells (16 vs. 11) — a genuine improvement, not overfitting, since `bet.p` (and therefore both the message's headline rate and `computeLiveOdd`'s live fair-odds target) now reflects the TL-matched pool automatically. The alert message also shows a `tlPaceLine()` — current goals vs. the match's own TL — so ahead-of/behind-pace context is visible even where the fallback pool is used.

**Walk-forward validated (2026-08-22, pre-TL-split baseline):** 34,596 flagged (HT-state, bet) instances across 10 held-out months — 65.9% claimed vs. 64.5% realized hit rate, well-calibrated (unlike L123's original point-estimate gate). Note this validates the *historical signal claim* only (does a goal happen somewhere in the 2nd half); it can't validate the exact "still nothing by minute 70 specifically" timing against real minute-level data, since `goals_time2` (the only source with real goal minutes) has no favourite/odds designation to replicate the signal selection — see `telegram/live_odds.js`'s header comment.

**No bookmaker lists any of the 4 LATEGOAL bet types directly** — but every one of them is mathematically equivalent to a real, standard market once you condition on the score being unchanged since HT (`equivalentRealMarket()` in `notify.js`):
- `favScored2H`/`homeScored2H`/`awayScored2H`: if that side has 0 goals so far and the opponent has ≥1, "this side scores" = **BTTS Yes** (the opponent already satisfied BTTS's other half).
- `over05_2H` ("any goal happens"): always equivalent to **Over (current total + 0.5) FT** — e.g. still 0-0 → Over 0.5 FT; still 0-2, 2-0, or 1-1 → Over 2.5 FT; still 0-1 or 1-0 → Over 1.5 FT.

When the equivalence applies, the alert calls `apifootball.js`'s `verifyBet365Price()` for that *real* market instead of showing only the internal Poisson estimate — same api-football integration L123 uses, `overTL`/`btts` were already supported market types.

**Live fair-odds estimate:** `telegram/live_odds.js` is a Node port of `static/app.js`'s `computeLiveOdd` (verified to produce identical output) — used to time-decay the HT-anchor hit rate down to a live fair probability/odds at the current minute, given no goal has happened yet.

**Strategy QUIET2H — "expect a quiet 2nd half" watch** (`notify.js` + `config.js`, added 2026-08-23): the mirror image of LATEGOAL. Fires once per match right at halftime — within the same `HT_SNAPSHOT_WINDOW` (44'-50') the HT-score snapshot itself is captured in, so it doesn't wait for a condition to hold first (unlike LATEGOAL) but also can't fire arbitrarily late into the 2nd half if a scan cycle is missed — if the match's own closing Total Line is low (`QUIET2H_TL_BANDS`, default `<2` and `2-2.5` only) and the HT-conditioned historical pool (fav line/side + TL band + exact HT score) shows a qualifying `under05_2H`/`under15_2H` bet.

**Market equivalence, same trick as LATEGOAL run in reverse** (`equivalentRealMarketQuiet2h()`): QUIET2H fires the moment 2H starts, so the current score always equals the HT snapshot — "no more goals in 2H" (`under05_2H`) always equals "FT total stays at the current total", and "at most 1 more goal in 2H" (`under15_2H`) always equals "FT total rises by at most 1". Both re-express as a standard, directly quotable **Under Total Goals FT** market api-football already supports (`underTL`): e.g. HT 1-0 or 0-1 (current total 1) → `under05_2H` = Under 1.5 FT, `under15_2H` = Under 2.5 FT. Same `apifootball.js` call L123/LATEGOAL use, just with the computed line as `ctx.avgTl`.

**Research + walk-forward validation (2026-08-23):** Total Line band is by far the dominant driver of a quiet 2nd half — TL`<2` shows ~32-39% under05_2H / ~70-75% under15_2H (vs. 22.2%/54.9% pooled baseline), TL `2-2.5` shows a smaller but still real elevation (~25-33%/~60-67%), TL`>=2.5` shows no edge at all (excluded by default). Walk-forward: 79 qualifying (fav_line/side, TL band, HT state) cells across 10 held-out months — 50.6% claimed vs. 49.1% realized (1.5pp gap), tighter than even LATEGOAL's own TL-banded calibration. Two follow-up movement checks were tested and **rejected** — neither survives walk-forward on top of the TL-band+HT-state query: `tl_move` showed no residual effect once TL band is controlled for, and `under_move=IN`/`over_move=OUT` (Over/Under odds steaming toward Under) showed a real pooled effect (z≈3 in the TL `2-2.5` band) but widened the calibration gap from 0.3pp to 1.5pp and shrank coverage by ~4x once stacked on the HT-state split — the plain TL-band query was already better calibrated on its own.

**Strategy FOCUS — 1T/2T Over/Under 0.5/1.5 watch** (`notify.js` + `config.js` + `focus_lib.js`/`focus_select.js`, added 2026-08-29, PLAN_FOCUS_BETS.md): the only strategy in this codebase whose candidate set is fixed **entirely offline** rather than swept live — `telegram/focus_config_search.js` walk-forward + cross-fit searches the 7 in-scope keys (`over05_1H`/`over15_1H`/`under05_1H`/`over05_2H`/`over15_2H`/`under05_2H`/`under15_2H`) over `CrossBooks/Bet365_Data_months` and writes surviving `(fav_line, fav_side, TL band, tier, TL move, Over/Under move, [HT state for 2H keys])` cells to `telegram/data/focus_configs.json`. At alert time, `focus_select.findMatchingCell()` just checks whether the live match's own bucketed dims string-match one of those cells (built by the exact same `focus_lib.compositeKey()` function used offline, so there's no risk of the live matcher and the offline search drifting apart) — no live argmax, so no cross-fit needed at alert time either (same reasoning QUIET2H/LATEGOAL use).

Fires the 3 1H keys in the same pre-kickoff window L123 uses (`FOCUS_PRE_WINDOW_MIN`, default 10 min), and the 4 2H keys at HT (`HT_SNAPSHOT_WINDOW`). Real-market equivalence for the 2H keys generalizes LATEGOAL/QUIET2H's own trick to all 4 (`focus_select.equivalentRealMarketFocus2h`): `overNH_2H`/`underNH_2H` (fired at HT, before any 2H goals) always equals `Over`/`Under (currentTotal + threshold - 0.5) FT`. The 3 pre-kickoff 1H keys have no such equivalence (the "already scored" reduction only applies once part of the match has been played scorelessly) — always shown unverified.

**A real pricing-model bug was found and fixed before this was trusted at all — see BETTING_EDGE_ANALYSIS.md's "Focus bets" section for the full story.** The historical backtesting price (`focus_lib.impliedPrice`, needed because the CrossBooks CSVs have no real settled price for half-time O/U lines) was systematically biased — Over keys overpriced by the model, Under keys underpriced, by 2.6-4.5pp each — which alone manufactured ~30 look-alike "edges" that vanished once corrected (`focus_lib.computeCalibration`, walk-forward-safe: derived from train rows only, never the test month). **As of 2026-08-29, focus_configs.json has very few surviving cells** (most of the 7 keys have none at all) — this is intentional conservatism, not a bug: FOCUS stays silent for a key with no validated cell rather than falling back to an unvalidated guess. Re-run `focus_config_search.js` periodically as more months of data accumulate.

**Exchange playbook (`telegram/focus_exchange.js`, `node focus_exchange.js --demo`):** calculators for running a FOCUS pick on Betfair/Smarkets instead of a soft-book bet-and-hold — time-decay lay (green up an Under lay as the Over price drifts with no goal), back-then-lay split (equal-green or free-bet), laddered entry (split stake across HT/60'/70' instead of one lump bet), book-vs-exchange arbitrage check, and a model-derived "cut minute" (when `live_lo` drops below what the current lay price implies). All driven by the same `computeLiveOdd`/`computeLive1HOdd` curves the strategy itself prices with.

**Strategy LIVEWATCH — live probability threshold watch** (`notify.js` + `config.js`, added 2026-08-29, revised same day): the broader ask behind FOCUS — "tell me when a bet's live probability crosses a threshold and it hasn't happened yet" — for **any** live match, not just the sparse cells `focus_config_search.js` validated offline. Uses the plain historical hit-rate for the match's own fav-line/side + closing-TL band (+ exact HT score for the 2H keys) — the same numbers already shown in the web UI's "1T/2T Goals Focus" panel — decayed live via `computeLiveOdd`/`computeLive1HOdd`.

- **Two gates, both required:** (1) a STATIC baseline-edge check — the Wilson CI lower bound of this match's own conditioned pool must clear a LESS-conditioned baseline pool (fav-line/side only for 1H keys; fav-line/side+TL-band for 2H keys) by `LIVEWATCH_MIN_EDGE` pp (default 0) — same "cfgRows vs. baseline" shape L123/QUIET2H use; (2) the LIVE-DECAYED probability, using that same CI-lower bound as the anchor (not the raw point estimate — same discipline as every other strategy here), must clear `LIVEWATCH_THRESHOLD_PCT` (default **75**).
- **Timing:** the 3 1H keys are checked every scan cycle up to minute 45 (no natural single check-point exists pre-HT). The 4 2H keys fire only within `LIVEWATCH_TRIGGER_WINDOW_2H` (default **68'-72'**, "around minute 70") — windowed like `LATEGOAL_TRIGGER_WINDOW`, not continuous through the whole 2nd half.
- **Minimum odds** shown in the message is the model's own CI-lower-bound-implied price (`100 / live_lo`), never derived from the raw point estimate.
- **Keys:** the 7 `focus_lib.FOCUS_KEYS` O/U bets plus 4 "team to score" keys added 2026-08-29 at the user's request — `homeScored1H`/`awayScored1H`/`homeScored2H`/`awayScored2H` (`LIVEWATCH_EXTRA_LABELS` in `notify.js`) — already fully supported by `engine.js`'s `BETS` list and both live-decay functions, so no new pricing logic was needed. `LIVEWATCH_KEYS` (config.js) restricts which of the 11 it watches.
- **Fires once per match+key** (24h `Dedup`, same as every other strategy) — NOT a live-updating message. "Updated every scan cycle" was clarified (2026-08-29) to apply to the **web UI** only (the Live tab already re-polls and recomputes every cycle); Telegram stays a one-shot alert.
- **Explicitly unvalidated** — no walk-forward check backs the threshold itself, unlike L123/LATEGOAL/QUIET2H; treat it like NEWMODEL, a real-time convenience alert to sanity-check against the message's own `n`, not a backtested strategy.
- Verified via `telegram/test_livewatch_logic.js` against the real production dataset (not a mock) — confirms the decay direction is correct (unders rise, overs fall, as time passes with no goal), that a goal flips a bet to `alreadyDecided` so it stops being watched, that the CI-lower-bound decay never exceeds the point-estimate decay, and that the 4 extra "team to score" keys are supported by both live-decay functions.

**Web UI "above baseline" filter** (`static/app.js`, added 2026-08-29, same user request as LIVEWATCH): the Live tab's "1T/2T Goals Focus" panel (`renderFocusMarketsPanel`) now only ever shows bets where `bet.edge > 0` (strictly above the unfiltered baseline rate) — a bet at or below baseline isn't a live signal, it's noise. Each row's headline number is now `bet.mo_lo` labeled "advised odds" (the conservative CI-lower-bound target price, matching `kellyLine()`/`realPriceVerdict()`'s convention everywhere else in this codebase), with the raw fair odds (`bet.mo`) shown as a secondary stat. `FOCUS_MARKET_BETS` was extended with the same 4 "team to score" keys LIVEWATCH watches (`homeScored1H`/`awayScored1H`/`homeScored2H`/`awayScored2H`, labeled "Home/Away to score 1T/2T"). This naturally satisfies "updated live every scan" — `pollLiveMatches()` already re-fetches and recomputes every `LIVE_POLL_MS` (60s) with fresh live-decayed numbers; no new polling logic was needed, only the filter/label change. (The panel itself now always renders inside the live-match detail modal — see "Opportunities feed" under Live Games Tab above, which replaced the old per-mode "🏆 BEST FOCUS BET" banner/`topFocusBet` with one cross-market Opportunities feed.)

**Testing caveat:** `notify.js` has no `require.main` guard — `require('./notify.js')` from anywhere (including a REPL or another script) runs the real scheduler immediately, fetches live matches, and can send real Telegram alerts from every already-enabled strategy, not just FOCUS. Test FOCUS logic in isolation via `telegram/test_focus_select.js` (pure functions, no network/Telegram) rather than requiring `notify.js`.

## Live Match & Odds Feed (`telegram/livescore.js`)

Adapted from `functions/api/livescore.js` for Node ≥ 18 native fetch. **Bet365 is now the primary (and only) live book** — it carries both the match list and odds, so Pinnacle can no longer be auto-discovered but Bet365's hash can. Odds are aliased onto `match.bet365_odds`, the field name Strategy L123 reads for its live price gate. Hash auto-discovery/fallback logic otherwise mirrors `functions/api/livescore.js` (see below).

**Optional — `telegram/apifootball.js`:** independent Bet365 price verification via api-football.com, purely informational — it does **not** change whether an alert fires (that decision is made entirely by each strategy's own logic before this runs). If `APIFOOTBALL_KEY` is set in `config.js`, `notify.js` calls `verifyBet365Price(betKey, ctx, key)` once, right before sending an alert, for whatever bet was just picked (L123, or the equivalent real market LATEGOAL/QUIET2H substituted in), and appends an "✅ ODDS OK" / "⚠️ ODDS LOWER" / "🔍 not available" line to the message — so there's no need to open Bet365 manually to check. Only called at alert-send time, never on every scan cycle, since the free plan caps at 100 req/day (2 calls per alert: one fixture lookup, cached per match, plus one odds lookup). Covers the markets api-football reliably lists as a single matchable value: Asian Handicap (`ahCover`/`dogCover`), Goals Over/Under (`overTL`/`underTL`), Match Winner (`homeWinsFT`/`awayWinsFT`/`drawFT`), and Both Teams Score (`btts`) — the other ~24 bet types (half-specific/derived stats like `favWins2H`) return `{ supported: false }` immediately, no API call spent, and the message says the check wasn't available for that market, unless LATEGOAL/QUIET2H's equivalence trick substitutes in one of the supported ones. Leave `APIFOOTBALL_KEY` unset to disable entirely — alerts fire exactly as before, just without the extra line.

**Daily budget guard (`telegram/api_budget.js`, added 2026-08-23):** both `apifootball.js` (alert-time verification) and `track_record.js` (settlement) route every real API call through a shared in-memory tracker, since both draw on the same 100 req/day quota. Rather than one shared counter, the quota is split into two independent, non-overlapping pools — `APIFOOTBALL_NOTIFICATION_BUDGET` and `APIFOOTBALL_SETTLEMENT_BUDGET` — so neither can ever borrow from or starve the other; exhausting one pool has zero effect on the other's remaining allowance. A refused settlement call throws an error its own per-entry `try/catch` already handles gracefully, simply retrying on the next 30-min cycle with nothing lost. Resets at UTC midnight; resets early (fresh budget) on a process restart, since it's in-memory only, matching the existing `_fixtureCache` pattern. **Currently: notifications get the full 100, settlement gets 0** (all quota reserved for live alert-time checks for now) — `settlePendingAlerts` still runs every 30 min but every api-football call it attempts is refused, so alerts stay logged-but-unsettled until `APIFOOTBALL_SETTLEMENT_BUDGET` is set back to a positive value.
